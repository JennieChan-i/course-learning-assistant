- small embedding 输出512维；诊断样例的相关段落重排分4.082，无关段落−10.195。分值不是正确概率。

- 显存数字是该进程的 PyTorch allocated peak，不包括桌面、驱动和其他进程；主题查询只用于时延检查，没有独立 gold 标签，不代表检索质量。

## 公开样例检索消融

16个独立自编片段，开发集60题，其中40题可回答；每种方法单并发、预热后运行。相关性标签是候选稿，尚未独立人工审阅。

| 方法（small embedding） | Recall@10 | NDCG@5 | P95毫秒 |
|---|---:|---:|---:|
| BM25 | 0.975 | 0.9064 | 0.40 |
| 向量 | 1.000 | 0.8370 | 3.62 |
| 混合 | 1.000 | 0.9065 | 2.80 |
| 混合＋重排 | 1.000 | 0.9423 | 25.54 |

base embedding 的混合＋重排 NDCG@5 同为0.9423，P95为32.82ms，峰值显存约765.6MB。未达到≥0.03的增益条件，所以保留small。特别注意：样例库仅16片段，候选上限20会覆盖全库，不能据此判断更大真实课程中两种embedding等效。

锁定测试集60题（40题可回答）结果：混合NDCG@5为0.8728，加入重排后为0.8570，**出现下降**。我保留这个失败结果，不使用测试集重新调参，也不宣称重排稳定增益。需要重新审核标签、分析失败问题，并在新的独立数据上验证。正式质量验收尚未通过。

## 实际遇到的问题

1. GPU安装临时文件落在C盘造成空间不足：将TEMP/TMP和缓存移至项目目录后完成安装。
2. 本机8000端口被占用：默认改为8765，没有停止其他服务。
3. base embedding仓库的权重格式与其他模型不同：下载脚本识别safetensors或pytorch_model.bin，并检查权重实际存在。
4. 模拟协议测试故意返回未读取来源的题目时被拒绝：补全测试夹具中的真实工具读取后通过；生产中保留此验证。
5. 重排在锁定测试集排序质量下降：保留失败，待人工标签与新数据分析，不回头调测试集。

## 真实 API 接入记录（2026-10-25）

使用者配置的阿里云百炼 `kimi-k3` 已通过原生工具调用和流式输出检查。接入时发现固定温度0.2不被接受，因此改为默认省略温度，支持可选 `LLM_TEMPERATURE`。工具调用设为串行，课程内取得证据后直接进入生成，减少无用往返。

一轮私有课程答疑完成，来源编号校验通过，总耗时约54.78秒，包含首次加载本地模型。该结果没有达到首版响应时延目标，不能将其称为正式质量验收通过。三题生成在原45秒请求超时下失败，因此将请求超时改为可配置 `LLM_TIMEOUT_SECONDS`，默认120秒。延长超时只是避免过早中断，不等于提高速度。

测试使用独立数据库 `runtime/live-private/smoke-tests/`，没有把测试成绩写入正式学习档案。私有文本、密钥、完整响应和原始测试记录均留在本地。

初次出题的独立检查拒绝了证据不足的题目，修订又触发3500输出预算上限。随后收紧题目长度与主题，审核时优先提供实际引用片段，并为思考模型设置6000结构化输出预算与32768上下文上限。三题生成及独立审核成功，本轮77.18秒。这个样例验证流程可执行，不证明整体题目质量或学习效果。

随后完成同一轮的真实评分与教练反馈，耗时95.14秒，三份测试作答分别得到6/6、4/6、0/6。它们不是人工gold，不能据此声称评分准确率。测试问题合并为一个知识点复习记录，正式学习数据库不受影响。该速度明显不适合频繁即时练习；后续需要用相同质量标准比较更快的模型或服务，再由使用者决定是否替换。

## 真实批量问答与评分（2026-10-25）

在自编16片段课程上，执行60条开发集问答（40条可回答、10条无答案、10条对抗）。基线有1条请求失败，2条自动引用ID检查不通过；其中模型拒绝伪造来源时复述了假编号。真实密钥匹配泄露计数为0，测试数据库未写入练习或复习记录。没有人工事实主张标注，不能计算证据支持率或无答案正确率。

基线首次内容P50为18.52秒、P95为43.26秒，完整回答P50为22.34秒、P95为46.65秒。另一评分任务可能共享GPU与服务商，并非单并发性能验收。即使如此，这组观测也表明当前模型交互仍慢，不能宣称≤8秒/≤25秒目标通过。

我合并了意图理解与检索调用，缩短解释Skill，加入分块引用校验及拒绝中的伪造编号处理。随后对15条明确选择的开发回归（5条答疑、10条对抗）重新运行：请求错误0、无效引用ID 0、被拦截假引用0、密钥匹配泄露0、练习/复习写入0。这只是修复回归，不替代完整60条新版本验收，也不证明回答事实全部正确。

评分基线将40份候选作答按三份一批分别运行单角色和双角色，共28批。两流程均完成34份有效评分，各有2批失败：结构错误、请求超时或验证失败。原运行累计耗时单角色670.61秒、双角色939.70秒；返回usage合计分别为46,745和76,248 Token。31份配对成功记录中4份总分不同。**一致或不一致都不是准确率**；本轮两流程的评分任务与证据标准保持一致，双流程额外增加教练辅导，它不能单独证明分工提高评分质量。

修复后单独复测4个失败批次，单角色6份、双角色6份均成功，耗时61.68与111.46秒。版本发生变化，我保留为新报告，不能把成功复测拼接成一次“原实验40/40全成功”。结构修复最多一次，时间超限不会无限自动重试。Token为服务实际返回的usage；超时未返回的usage不代表没有产生费用。没有配置账户实际单价，不推算费用。

公开报告：`answers-dev-baseline.json`、`answers-dev-regression.json`、`grading-baseline.json`、`grading-recovery.json`，均位于本目录的 `reports/`。只有自编数据进入公开报告；私有课程原文与学习档案留在本地。

## MCP 与真实取消验证（2026-10-25）

免密入口能初始化和发现工具，但搜索返回服务端额度限制。正式学习环境的本地计数为0，这不是“300次已经用完”。300是项目保护上限，账户免费credits与免密限额是不同机制。

使用者填写自己的免费API Key后，真实MCP基础搜索成功返回5个结果。随后验证模型原生 `search_web` → MCP发现与调用 → 外部引用回答，保留课程与网页来源共6条。第一次返回第三方文章，回答明确说明并非官方原文；加入 `include_domains` 后，第二次取得 Tavily 官方文档。两次集成检查分别保存，不隐藏第一次来源质量不足。检查使用隔离数据库，不污染正式学习历史。

真实HTTP取消检查初次失败：装饰器HTTP中间件影响了断开信号。改为纯ASGI边界后，用真实本机TCP连接发起出题并断开，验证在途任务取消、任务锁释放、无练习写入。该回归进入CI；不是仅用模拟Request对象证明取消可用。

## 推理力度的小样本对照

为避免仅通过换模型掩盖问题，我在同一 `kimi-k3` 上，用三个自编课程问题比较服务默认推理与 `reasoning_effort=low`，预热模型、顺序请求。默认首次内容为14.81、27.33、33.08秒，完整回答16.90、30.02、37.45秒；low首次内容9.27、7.36、7.96秒，完整回答11.51、10.58、13.96秒。六次均完成，原始回答与Token保存在 `reasoning-effort-exploratory.json`。

这是每种三题的小样本，不是P95验收，也没有独立人工质量评分。它支持进一步验证轻度推理，不能证明质量不变。当前只为学习教练配置 `LLM_COACH_REASONING_EFFORT=low`，评估员保持服务默认；通用 `LLM_REASONING_EFFORT` 留空。新增15条开发回归另存结果，不能覆盖默认推理基线。

服务商的模型专页与通用API页对推理参数的描述存在差异，因此以本次真实调用确认参数可接受；不将此结论推广到不同地域、接口或模型。参考[通用API文档](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-chat-completions)与[Kimi说明](https://help.aliyun.com/zh/model-studio/kimi-api)。复现脚本为 `scripts/check_live.py`，会真实消耗一次MCP搜索及LLM调用，默认只使用自编课程。

只给教练设置low后，15条开发回归再次完成：请求错误0、无效引用ID 0、拦截假引用0、真实密钥匹配泄露0、练习/复习写入0，报告为 `answers-dev-coach-low.json`。该集合首次内容P50为10.16秒、P95为36.15秒，最长完整回答38.96秒，仍有明显长尾，未达到整体时延目标。集合包含10条对抗输入和初次加载影响，不代替预热真实课程单并发验收；事实支持程度仍需人工核对。
